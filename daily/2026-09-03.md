## 1. 入职 90 天融入计划器

**Prompt：**
```
Act as an onboarding strategist. I'm starting a new role: [job title] at [company type/industry]. My background: [past experience]. The team is [size/culture hints]. Create a 30-60-90 day plan that:
- Days 1-30 (Learn): who to meet, what systems to master, 3 questions to ask each stakeholder, how to build a "how things actually work here" map (not just the org chart)
- Days 31-60 (Contribute): small visible wins that don't require full context, how to get feedback loops set up, who to align with on expectations
- Days 61-90 (Lead): what to propose changing, how to frame it as experiments not criticism, first "signature deliverable" ideas
- Include weekly reflection questions and 2 "quick credibility" moves per phase
Output as a timeline table with concrete actions, not platitudes.
```
> 来源：AI Academy (Techpresso) — 2026 career & onboarding prompt workflows
> 用法：新工作前 90 天分三阶段：先学再贡献后主导，附每周反思题与快速建立信任的具体动作。

## 2. 会议纪要行动项追踪器

**Prompt：**
```
Act as an action-item tracker. Here is my meeting transcript/notes: [paste]. Extract and structure:
1. Every decision made (with who decided and what was agreed)
2. Every action item: owner, exact deliverable, due date (or flag if none stated), and who it depends on
3. Open questions that were deferred, with the person responsible to answer
4. Risks/blockers mentioned but not resolved
5. Things discussed but explicitly NOT decided (to avoid false assumptions later)
Then: (a) flag any action item with no clear owner or no due date, (b) draft a 5-line summary email to send attendees confirming decisions + action items, (c) suggest the 2 items most likely to silently die and how to prevent that.
```
> 来源：SurePrompts / AI Academy — meeting follow-up prompt libraries 2026
> 用法：会后就地生成决策清单、行动项（含负责人/截止日）、悬而未决问题和跟进邮件，专治「会后没人认领」。

## 3. 授权与放手决策器

**Prompt：**
```
Act as a delegation coach. My current task list: [paste 8-15 tasks with rough time each takes]. Team/situation: [who could take work, their skill levels, my constraints]. For each task decide: Do / Delegate / Defer / Delete, using this logic:
1. Is this the highest-value use of MY time right now? (strategic, relationship-critical, needs my judgment)
2. Can someone else do it 80% as well? If yes, delegate — with a 3-step handoff: context + expected standard + check-in point
3. If delegating, tell me exactly what to say in the handoff message, including how to describe "done" without micromanaging
4. For tasks I keep: batch them by context to protect deep work
Output a table (task | decision | why | handoff message or schedule slot). Be blunt about tasks I'm hoarding out of habit.
```
> 来源：AI Academy (Techpresso) — productivity & leadership prompts 2026
> 用法：把任务清单过一遍「做/授/延/删」四象限，该放手的任务直接给出交接话术与验收标准，避免习惯性囤活。

## 4. 冲突优先级裁决器

**Prompt：**
```
Act as a prioritization referee. I have two (or more) urgent items that collide:
- Task A: [what, deadline, who's waiting, cost of missing it]
- Task B: [same details]
Constraints: [my available hours this week, other commitments]
Decide for me using this framework:
1. Consequence severity: what actually happens if each slips (quantify: money, trust, missed legal/contractual deadline)
2. Reversibility: which decision is easier to undo later?
3. Stakeholder leverage: who escalates fastest and what they control
4. Deadline reality: are the deadlines real or self-imposed? Which can be renegotiated with a 1-line ask?
Then give me: a clear verdict (A first / B first / partial overlap plan), the exact renegotiation message if one deadline can move, and what to say to the person waiting on the losing task.
```
> 来源：Gmelius / Forbes — executive productivity prompts (2026 roundups)
> 用法：两个都「紧急」时不再凭感觉：用后果严重度、可逆性、干系人杠杆和截止日期真假四个维度裁决，并附沟通话术。

## 8. 文风指纹提取器

## 9. 长文结构诊断医生

**Prompt：**
```
Act as a structural editor, not a line editor. Here is my draft article: [paste]. Diagnose its architecture:
1. The promise check: does the intro actually promise what the body delivers? Restate the article's real thesis in one sentence — if I can't, the thesis is unclear
2. Flow map: outline the current section logic; flag sections that repeat, digress, or arrive out of order (e.g., solution before problem)
3. Reader-energy curve: where will readers get bored (long stretches without payoff) or confused (missing bridge)? Mark exact spots
4. Missing elements: where a concrete example, counterargument, or "so what" is needed
5. The cut list: what to delete or move to a footnote to make the spine visible
6. A restructured outline (2 versions: safe restructure and bold restructure) with one-line rationale per change
Give me the diagnosis first — don't rewrite the whole piece unless I ask.
```
> 来源：Coursiv — Claude AI for writing in 2026 (outline-first editorial workflows)
> 用法：只看结构不动词句：检查承诺兑现、章节逻辑、读者能量曲线、缺失要素，输出「保守重构」和「大胆重构」两版大纲。

## 10. 技术内容小白视角改写器

**Prompt：**
```
Act as a technical writer who remembers what it's like to be a beginner. Here is a technical document/README/guide: [paste]. Rewrite it for a reader who is smart but new to this domain. Rules:
1. Lead with what the reader can DO after reading, not with the technology's history
2. Define every unavoidable term on first use in one plain sentence; move deep jargon to a glossary at the end
3. Replace abstract instructions with a concrete walkthrough: one realistic example running through the whole doc (same example thread, not new examples per step)
4. Add a "what could go wrong" note after each step where failure is common
5. Cut any sentence whose removal doesn't change the outcome
6. End with a 3-question self-check so the reader can confirm they got it
Output the rewritten version; keep all technical accuracy — simplify language, never the facts. Then list the 3 places where I had to make the biggest judgment calls so you can verify.
```
> 来源：Claude prompting best practices (Anthropic) / Coursiv writing guides 2026
> 用法：把技术文档改写成「读完就能动手」的入门版：同一示例贯穿全文、每步附常见错误提示，结尾给自测题验证理解。

## 16. 遗留系统现代化路线图

**Prompt：**
```
Act as a software modernization architect. Legacy system: [language/stack, age, size, what it does, who depends on it]. Problems: [pain points: slow deploys, can't hire, scaling issues, security]. Constraints: [team size, budget, can't stop the business, compliance]. Produce:
1. Strangler-fig strategy: which capabilities to extract first (highest pain / lowest coupling), in dependency order — NOT a big-bang rewrite
2. A 3-phase roadmap (stabilize → extract → replace) with concrete milestones, each with an exit criterion that proves business value before continuing
3. Risk register for the migration: what could silently go wrong (data drift, behavior differences, tribal knowledge loss) and a mitigation per risk
4. "Do not touch" list: parts that work fine and are cheaper to keep than to move
5. Metrics to prove progress to stakeholders (deploy frequency, MTTR, defect rate per module)
6. The 3 mistakes teams most often make in this exact situation and how to avoid them
Output a roadmap document I can share with my team.
```

> 用法：用「绞杀者模式」而非推倒重来：先抽取痛点最高、耦合最低的能力，三阶段路线图每步都有业务价值的退出标准。

## 17. 性能瓶颈假设生成器

**Prompt：**
```
Act as a performance engineer. My application: [describe stack + what it does]. Symptom: [e.g. "API responses slow under load", "page takes 6s to first paint"]. Before I profile, generate:
1. A ranked hypothesis list (5-7 candidates) of likely bottlenecks for THIS architecture: DB queries/N+1, missing indexes, blocking I/O, serialization, GC/memory churn, network latency, cache misses, connection pool exhaustion — ordered by prior probability given my stack
2. For each hypothesis: the cheapest measurement that would confirm or kill it (which metric, which tool, what threshold)
3. The "measure first" trap list: common fixes people apply that don't fix anything (premature caching, adding servers to a DB-bound problem)
4. A decision tree: based on what the first 3 measurements show, what to investigate next
5. What to capture NOW before changing anything (baseline numbers) so we can prove the fix worked
Keep it concrete — no generic "profile and optimize" advice.
```
> 来源：Claude Code / K2view prompt engineering guides 2026 (debugging & diagnostics)
> 用法：动手优化前先让 AI 按架构给出概率排序的瓶颈假设与「最便宜的验证测量」，避免拍脑袋加缓存/加机器。

```
Act as a cross-model prompt portability auditor. My prompt was built for [source model: ChatGPT/Claude/Gemini/other] and works well there. I want to use it with [target model(s)]. The prompt: [paste]. Audit its portability:
1. Feature dependency scan: does the prompt rely on source-model-specific capabilities that the target lacks or implements differently — tool use syntax, artifact/canvas behavior, image input handling, system-prompt-only features, reasoning-effort settings, structured-output mode, context window size assumptions?
2. Style triggers: does it use phrasing calibrated to the source model's default style (e.g., markdown-heavy formatting, XML tags, bullet density) that the target handles differently? Which instructions will need rewording?
3. Length & context assumptions: does it assume a context window or output limit the target doesn't have? (long documents, many few-shot examples, very long outputs)
4. Delimiter robustness: if it uses XML tags or special delimiters, does the target model respect them as reliably?
5. Rewrite recommendations: a ported version of the prompt for the target model with ONLY the necessary changes marked (diff-style: original line → ported line + reason)
6. Regression plan: the 5 test inputs to run on the target model to confirm parity, and what output differences are acceptable (wording) vs. deal-breakers (structure, accuracy)
7. Version note: a one-line header to add documenting which models this prompt version was validated on
Output the audit with a clear verdict: drop-in / needs minor edits / needs rewrite.
```
> 来源：Prompt Builder / Coursiv — multi-model prompt comparison guides 2026
> 用法：换模型前做可移植性审计：扫特性依赖、语气校准、上下文假设与分隔符鲁棒性，只改必要处并给出 5 条回归测试输入确认效果不掉。
